## Upstream summary
Upstream OpenQ4 rewrote the renderer's packaging and added two new backends while keeping the legacy path alive (278 files, ~154k insertions, 262 commits since fork abb9a688). Key architecture changes affecting reapplication: (1) Renderer module split — the renderer now builds as loadable modules (renderer-gl, renderer-vk) behind a versioned extern-C ABI (RenderModuleAPI.h, RENDER_API_VERSION 7; RendererModule.cpp/RendererGLModule.cpp); idRenderSystem/idRenderWorld/idMaterial vtable layouts and renderEntity_t layout are ABI-checked, so ANY openPREY interface/struct addition forces an ABI version bump and dual-backend consideration; GL typedefs were severed from renderer headers and the engine owns window/context state via SDL3 window services. (2) New Vulkan renderer (src/renderer/Vulkan/, ~40k lines incl. SPIR-V shaders) reaching retail-parity phases G. (3) A ModernGL clustered/executor path (ModernGLExecutor ~10.7k lines, ScenePackets, RenderGraph, ModernClusteredLighting, ModernShadowPlanner) ADDED ALONGSIDE the legacy path — RB_STD_DrawView, RB_STD_T_RenderShaderPasses, RB_CreateSingleDrawInteractions and the full ARB2 backend all still exist; draw_arb2.cpp grew to ~12k lines (ARB2-bypass hardening, shadow-map ARB2 parity, Apple GL2.1 fallbacks) — ARB fragment programs are still fully supported, answering the key question: Prey's ARB-program material features can still target the ARB2 path. (4) Image/material pipeline extraction — Image_files/Image_process/Image_program/BinaryImage/DXT/Color/jpeg-6 moved to a shared src/imagetools static library (with BC7/RXGB DDS support superseding openPREY's DDS loader); tr_trisurf and geometry code moved to src/render_geo; ImageManager/Image_load were restructured but keep the fork-era function skeleton. (5) Feature convergence: because both repos share an author, openPREY's SSAO/bloom/HDR-scene-target/tonemap/CRT post stack, light-grid irradiance system (now 3453-line RenderWorld_lightgrid.cpp with .lightgridpack format and residency management), r_mode -2 desktop mode, GuiTrace animated-model support, EvaluateRegisters sound-emitter parameter, fragmentParm parsing, and a dozen portability fixes ALREADY EXIST upstream in more evolved form — these openPREY changes should be dropped, not reapplied. Also new upstream: shadow mapping (7-phase persistent atlas system), lens flares, SMAA, TrueType fonts, cel shading, MaterialResourceTable decl caching, Model_md5r, DI_REFLECTION/REFRACTION_RENDER subview classes. What upstream does NOT have (must be reapplied): all Prey-specific compat and features — beam/particle models, HUMANHEAD surface/content tables, portal/skybox subviews, spirit-walk visibility, glow overlay, SL_INTERACTION ARB material stages, corona deform, shaderLevel gating, view-mode expressions, D3 .proc header support, legacy image-name remaps, and the Prey game-facing renderer API surface.

## Notes
Working-tree caveats: src/renderer/RenderWorld_lightgrid.cpp is UNTRACKED (never committed) and ~16 renderer files carry uncommitted modifications (mostly lightgrid, post-process ordering, image remaps) — the catalog treats the working tree as current state per instructions. Cross-pollination is the dominant theme: openPREY and OpenQ4 share an author, and roughly a third of openPREY's renderer diff (post stack, lightgrid, image-manager fixes, portability) already exists upstream in more evolved form — a naive rebase would create duplicate implementations, so RD-10/RD-11/RD-13/RD-22 should be consciously DROPPED in favor of upstream. The single biggest structural cost of the rebase is the renderer module ABI: every idRenderSystem/idRenderWorld virtual and renderEntity_t field openPREY added (RD-01, RD-08, RD-14, RD-16, RD-20) now requires a RENDER_API_VERSION bump and a Vulkan-side stub/implementation decision, because upstream version-checks vtable/struct layout across the engine/renderer-module boundary. Second biggest: Prey-specific backend features (RD-05 SL_INTERACTION, RD-09 glow) land in a draw_common/draw_arb2 that grew ~23k lines combined; they remain feasible because upstream deliberately kept the legacy RB_STD_/ARB2 path alive alongside ModernGL and Vulkan, but each needs an explicit decision about whether it must also work on the ModernGL clustered path and Vulkan (initial recommendation: port to the legacy GL path first, gate Prey rendering to renderer-gl/BE_ARB2, treat ModernGL/Vulkan parity as follow-up work).
